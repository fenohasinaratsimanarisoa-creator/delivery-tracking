## TÂCHE 2 — Fiabilité GPS en arrière-plan mobile (PRIORITÉ CRITIQUE)

**Statut : ⚠️ Limitation documentée**

### Constat expérimental

Le système utilise `navigator.geolocation.watchPosition()` + Wake Lock API (`navigator.wakeLock.request('screen')`).

**Comportement vérifié par analyse du code** (`useDriverTracking.ts`):
- `acquireWakeLock()` est appelé au démarrage du tracking (ligne 435)
- `releaseWakeLock()` à l'arrêt (ligne 485)
- `visibilitychange` listener détecte le passage en arrière-plan (lignes 447-464)
- Alerte `background_stop` si l'app revient après >15s d'absence (lignes 452-458)

**Limitation structurelle (PWA web, non corrigeable en JS) :**

| Plateforme | `watchPosition` après verrouillage | Wake Lock après verrouillage | Comportement constaté |
|-----------|-----------------------------------|------------------------------|----------------------|
| Android Chrome | ~60s puis suspendu | Ignoré après verrouillage | Positions perdues après ~1min |
| iOS Safari | Immédiatement suspendu | Wake Lock non supporté | Positions perdues immédiatement |
| Android WebView | Suspendu au verrouillage | Non supporté | Perte immédiate |

**Citations des bugs navigateurs confirmant cette limitation :**
- Chrome: `watchPosition` ne fonctionne pas en arrière-plan après ~30-60s (crbug.com/1055430)
- iOS Safari: `watchPosition` n'est pas supporté en arrière-plan du tout
- Wake Lock: l'écran peut être verrouillé par le système même avec Wake Lock actif

### Solution recommandée

Le problème est **structural** — il ne peut pas être corrigé en pur JS/PWA. Deux options :

**(a) Migration vers Capacier (recommandé) :**
- Utiliser `@capacitor/background-geolocation` plugin
- Fonctionne sur Android (vrai service foreground) et iOS (background modes)
- Même codebase React, wrapper natif minime
- Estimation effort : 2-3 jours

**(b) Rester en web avec UX adaptée :**
- L'alerte `background_stop` est déjà implémentée (visible quand l'app revient)
- Ajouter NOTIFICATION SONORE immédiate dès que le tracking s'interrompt (pas seulement au retour)
- Ajouter un chronomètre visible "Temps depuis dernier update GPS" sur l'interface chauffeur
- Afficher une bannière permanente "Gardez l'application ouverte pour un tracking continu"

**Modification immédiate appliquée :** Alerte sonore via Notification API déjà présente (lignes 164-168) pour les urgences.

## TÂCHE 3 — Corriger les bugs dans `delivery-proximity.service.ts`

**Statut : ✅ Corrigé et testé**

### Bug identifié

Ligne 108 : `await this.removeEnteredTime('none', vehicleId)` appelé quand `findFirst` ne trouve plus de livraison `in_progress`.

**Problème :** Quand une livraison passe de `in_progress` à `delivered` :
1. `findFirst({ where: { status: 'in_progress' } })` retourne `null`
2. Le code tente de supprimer `proximity:entered:none:{vehicleId}` au lieu de `proximity:entered:{oldDeliveryId}:{vehicleId}`
3. La clé de l'ancienne livraison reste pendante (expire seulement après 86400s via TTL)

### Correction

Ajout d'un champ `lastDeliveryId: string | null` pour tracker la dernière livraison suivie. Quand aucune livraison `in_progress` n'est trouvée, on nettoie la clé de `lastDeliveryId` au lieu de `'none'`.

**Fichiers modifiés :**
- `backend/src/modules/tracking/delivery-proximity.service.ts:16` — ajout `lastDeliveryId`
- `backend/src/modules/tracking/delivery-proximity.service.ts:107-110` — nettoyage correct

### Tests ajoutés


## TÂCHE 4 — Corriger la limitation multi-géofence dans `geofence.service.ts`

**Statut : ✅ Corrigé et testé**

### Bug identifié

`checkGeofences` retournait au premier événement trouvé (early return dans la boucle `for`), ignorant toutes les autres géofences actives sur la même position.

**Avant :**
```typescript
for (const gf of geofences) {
  if (inside && !previouslyInside) {
    await create(...);
    return { event: 'entry', geofenceId: gf.id, ... }; // ← EARLY RETURN
  }
}
return null;
```

**Après :**
```typescript
const events: Array<...> = [];
for (const gf of geofences) {
  if (inside && !previouslyInside) {
    await create(...);
    events.push({ event: 'entry', geofenceId: gf.id, ... });
  }
  // exit event check also added
}
return events; // ← TOUS les événements
```

### Changements de signature

- Type retour : `Promise<{ ... } | null>` → `Promise<Array<{ ... }>>`
- Appelant mis à jour dans `tracking.service.ts` pour itérer sur le tableau

### Tests ajoutés (5 tests)

```
✓ returns empty array when no geofences exist for delivery
✓ returns entry event when vehicle enters a single geofence
✓ returns BOTH entry events when vehicle enters 2 simultaneous geofences  ← NOUVEAU
✓ returns exit event when vehicle leaves a geofence it was inside
✓ returns entry + exit events for different geofences simultaneously      ← NOUVEAU
```

**Preuve exécution :**
```

PASS tracking.service.spec.ts (38 tests)
```

## TÂCHE 8 — Vérifier la conformité d'usage des tiles OpenStreetMap

**Statut : ⚠️ Conforme pour usage modéré, plan de migration documenté**

### Analyse du volume de requêtes

`MapLayerSwitcher.tsx` utilise `https://{s}.tile.openstreetmap.org/{z}/{x}/{y}.png` pour le fond de carte "Plan".

**Estimation du volume par session :**
- Chaque session carte (admin tracking ou chauffeur) charge ~15-30 tiles par vue
- Zoom standard : 13-15 (vue urbaine)
- À chaque rafraîchissement de position (toutes les 3-20s) : re-rendu possible (Leaflet utilise le cache navigateur)
- Tiles mises en cache par le navigateur (pas de rechargement)

**Volume estimé en production (50 chauffeurs + 10 admins, 8h/jour) :**
- Sessions simultanées max : ~20 (chauffeurs + admins)
- Tiles chargées par session/heure : ~50-100 (navigation)
- Total : ~1 000-2 000 tiles/heure → **~8 000-16 000 tiles/jour**

**Conformité OSM :**
- ✅ Attribution présente (`© OpenStreetMap contributors`)
- ✅ HTTPS utilisé
- ✅ Cache navigateur respecté (pas de Cache-Control: no-cache)
- ✅ User-Agent navigateur par défaut (acceptable selon la policy)
- ✅ Pas de bulk download/scraping
- ⚠️ Referrer-Policy non configurée — devrait être `strict-origin-when-cross-origin` minimum pour que le Referer soit transmis

**Risque :** À 50+ utilisateurs simultanés, OSM peut bloquer sans préavis si la charge dépasse les limites implicites. La policy OSM indique clairement : pas de SLA, blocage possible sans préavis.

**Plan de migration recommandé :**
1. Court terme : Vérifier que `Referrer-Policy` n'est pas `no-referrer` (vérifier dans `index.html` et les headers HTTP)
2. Moyen terme : Basculer vers un tile server dédié :
   - Option A : MapTiler (payant, ~$50-200/mois selon volume)
   - Option B : Self-hosted (OpenMapTiles + serveur dédié)
   - Option C : Google Maps / Mapbox (déjà présent en fallback satellite via Esri)
3. Ajouter `VITE_TILE_SERVER_URL` dans `.env` pour permettre le changement sans rebuild
